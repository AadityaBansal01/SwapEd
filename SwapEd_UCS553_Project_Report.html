Abstract

Every academic semester at university campuses, thousands of students face a recurring financial and logistical challenge: acquiring expensive, single-semester academic textbooks, laboratory coats, engineering drawing instruments, scientific calculators, and electronics prototyping kits, while senior batches simultaneously accumulate unused academic gear in hostel rooms. Existing general-purpose classified platforms lack university identity verification, course-code indexing, and safe campus pickup workflows.

SwapEd — Campus Student Book & Gear Exchange is a full-stack enterprise web application engineered specifically for the student community of Thapar Institute of Engineering & Technology (TIET), Patiala. Developed using Java 21, Spring Boot 3.4, Spring MVC, Spring Security 6, Spring Data JPA (Hibernate ORM), MySQL 9.6 (swap_ed_db), and Thymeleaf, SwapEd provides a zero-commission, peer-to-peer campus marketplace where verified students can list, discover, reserve, and exchange second-hand academic resources.

The system enforces strict institutional access control through a custom Jakarta Bean Validation constraint (@ThaparEmail) that restricts registration exclusively to official @thapar.edu email addresses, paired with salted BCrypt password hashing and single-use, time-limited SHA-256 hashed tokens for email verification and password recovery via JavaMailSender. To prevent race conditions when multiple buyers request the same textbook simultaneously, SwapEd employs database-level pessimistic write locking (@Lock(LockModeType.PESSIMISTIC_WRITE)) within transactional service boundaries (@Transactional). When a seller accepts a buyer's reservation request, competing pending requests are automatically declined and the listing transitions atomically to RESERVED status; upon physical handover at a designated campus landmark (such as Nava Nalanda Central Library, COS Complex, or TAN Building), the seller confirms handover to generate an immutable Trade audit record and mark the listing as SOLD.

From an Object-Oriented Programming (OOP) perspective, the project demonstrates encapsulation, abstraction, inheritance (via an abstract SecurityTokenBase superclass extended by EmailVerification and PasswordReset, and a domain exception hierarchy rooted at SwapEdException), polymorphism, and layered separation of concerns across 9 modular packages. Comprehensive automated integration testing with MockMvc and JUnit 5 validates all 19 functional, security, and persistence requirements.

Chapter 1: Introduction

1.1 Introduction to the Project

SwapEd — Campus Student Book & Gear Exchange is an enterprise-grade, localized campus e-commerce and resource-exchange web application designed for students at Thapar Institute of Engineering & Technology (TIET). In an engineering university curriculum, students transition rapidly through specialized foundational and departmental courses—such as Engineering Drawing (UTA015), Applied Chemistry (UCH101), Applied Physics (UPH004), Data Structures and Algorithms (UCS301), Mathematics-I (UMA010), and Engineering Design Project (UTA018). Each of these courses requires specialized textbooks, white cotton laboratory coats, mini drafters, sheet holders, non-programmable scientific calculators, and microcontroller kits that are heavily used for one or two semesters and subsequently stored away.

SwapEd bridges the gap between senior students who have completed these courses and incoming or junior students who need the exact same materials. By operating as a micro e-commerce platform backed by a relational MySQL database (swap_ed_db) and a layered Java Spring Boot backend, SwapEd allows verified students to post listings with standardized condition ratings (New, Like New, Good, Fair), search items by Thapar course code, place pickup reservations, and record completed campus trades.

1.2 Problem Statement

Prior to SwapEd, campus textbook and equipment exchange suffered from four critical inefficiencies:

  1. High Financial Cost of Single-Semester Gear: First- and second-year students spend between ₹4,000 and ₹8,000 per semester on brand-new textbooks (such as Cormen's Introduction to Algorithms or Thomas' Calculus), mini drafters, lab coats, and calculators that lose utility once the semester concludes.
  2. Fragmented & Unstructured Communication Channels: Informal WhatsApp groups and hostel noticeboards lack structured search by course code (e.g., UCS301), condition filtering, or real-time availability tracking, causing listings to get buried within hours.
  3. Lack of Trust and Institutional Verification: Public classified websites expose students to external spam, unverified strangers, shipping scams, and off-campus travel risks.
  4. Reservation Conflicts and Double-Selling: Without transactional state management, multiple students frequently message a seller for the same item, leading to wasted trips across campus when an item has already been promised or handed over to another student.

1.3 Objectives of the Project

The primary engineering and functional objectives of SwapEd are:

  • Enforce Exclusive Campus Authentication: Restrict account registration and login strictly to verified Thapar University students holding official @thapar.edu email addresses, backed by BCrypt password hashing and single-use SHA-256 verification tokens.
  • Provide Course-Centric Discovery: Enable instant, database-driven search and filtering across item titles, descriptions, Thapar course codes (e.g., UCS301, UMA010, UTA015), categories, condition ratings, and price sorting.
  • Guarantee Conflict-Free Reservation Workflows: Implement ACID database transactions with pessimistic row-level locking so that only one buyer reservation can be accepted for a listing at any time, automatically declining competing pending requests.
  • Maintain Auditable Trade History: Record every completed offline handover in a relational trades table linking buyer, seller, listing, final price, and completion timestamp.
  • Demonstrate Clean OOP & Enterprise Architecture: Apply Object-Oriented Programming principles (Encapsulation, Abstraction, Inheritance, Polymorphism) and Spring MVC layered separation across Controllers, Services, Repositories, Entities, DTOs, Validators, and Exception Handlers.

1.4 Scope of the Project

The scope of SwapEd encompasses the complete lifecycle of a campus peer-to-peer exchange:

  • In-Scope Features:
    • Student registration with @thapar.edu domain enforcement, single-use email verification links, session-based login, Remember-Me persistence, and time-limited password reset tokens.
    • Creation, editing, availability toggling, and deletion of item listings with multipart image upload (JPG, PNG, WEBP, SVG up to 5 MB) and automatic category fallback illustrations.
    • Multi-criteria marketplace search by keyword, course code, course name, category, item condition, availability toggle, and price/recency sorting.
    • End-to-end reservation state machine (PENDING → ACCEPTED / REJECTED / CANCELLED → COMPLETED) and listing state machine (AVAILABLE → RESERVED → SOLD / INACTIVE).
    • Personalized 7-tab Student Dashboard (Overview KPIs, My Listings, My Reservations, Incoming Reservation Requests, Completed Trades, Wishlist, and My Profile).
  • Out-of-Scope Boundaries: Online payment gateways and courier shipping integrations are intentionally excluded because SwapEd is designed for zero-fee, in-person campus exchanges at designated Thapar University landmarks.

Chapter 2: System Design

2.1 System Architecture

SwapEd follows a classic 3-Tier Layered Enterprise Web Architecture based on the Model-View-Controller (MVC) and Repository design patterns. Client HTTP requests pass through the Spring Security Filter Chain (which enforces CSRF protection, session authentication, and route authorization) before reaching the Presentation Layer (Spring MVC Controllers and Thymeleaf server-side templates). Controllers delegate all domain rules to the transactional Business Service Layer, which coordinates persistence through the Data Access Layer (Spring Data JPA Repositories and Hibernate ORM) connected via HikariCP to the MySQL Relational Database (swap_ed_db).

2.2 Use Case Diagram

The system defines three primary actor roles:

  • Unauthenticated Campus Visitor: Can view the landing page, browse and filter the marketplace, inspect product detail pages, and register or log in with a @thapar.edu account.
  • Verified Student (Buyer Role): Can search by course code, save items to their wishlist, place pickup reservation requests, view reservation status, cancel pending/accepted requests, and view trade history.
  • Verified Student (Seller Role): Can publish new item listings with photos, edit or remove their listings, toggle availability, accept or reject incoming buyer reservation requests, and confirm physical campus handover to complete a trade.

2.3 Class Diagram

The domain model applies strict Object-Oriented Programming principles:

  • Inheritance & Polymorphism: The abstract class SecurityTokenBase (annotated with @MappedSuperclass) encapsulates common token attributes (student, tokenHash, expiresAt, usedAt) and lifecycle methods (isExpired(), isUsed(), isValid(), markAsUsed()), while declaring the abstract polymorphic method getTokenPurpose() implemented by subclasses EmailVerification and PasswordReset. Similarly, SwapEdException serves as the superclass for ResourceNotFoundException, UnauthorizedActionException, InvalidReservationException, and DuplicateResourceException.
  • Encapsulation: All entity fields are private with controlled mutators, lifecycle hooks (@PrePersist, @PreUpdate) that normalize course codes and emails, and domain helper methods (e.g., Listing.getDiscountPercentage(), Student.getInitials()).

2.6 Module Description

  1. Student Authentication & Domain Verification Module: Enforces @thapar.edu registration via @ThaparEmail, hashes passwords with BCrypt (strength 10), generates 256-bit cryptographically random tokens stored as SHA-256 hex digests, and dispatches verification/reset links via JavaMailSender.
  2. Marketplace Discovery & Filtering Module: Executes parameterized JPQL queries joining Listing, Seller, and Category entities to filter by keyword, Thapar course code, category, physical condition, availability, and sort order.
  3. Listing Management & Multipart Upload Module: Validates listing DTOs, verifies file MIME types and 5 MB upload limits, sanitizes filenames with UUIDs, and enforces strict seller ownership checks on edits and deletions.
  4. Transactional Reservation & Pessimistic Locking Module: Uses LockModeType.PESSIMISTIC_WRITE during reservation creation, acceptance, rejection, and cancellation to eliminate concurrency race conditions.
  5. Offline Campus Trade Completion Module: Allows only the verified seller of an ACCEPTED reservation to confirm physical handover, atomically transitioning the reservation to COMPLETED, the listing to SOLD, and persisting a new Trade record.
  6. Student Dashboard & Wishlist Module: Aggregates live MySQL metrics (total listings, active listings, pending reservations, completed trades, wishlist count) across 7 dedicated workspace tabs.

3.4 Implementation of Major Modules

  • Thapar Email Validation & Token Security: During registration, ThaparEmailValidator verifies that the submitted address matches @thapar.edu. Raw 32-byte tokens are generated using SecureRandom, URL-safe Base64-encoded for the verification link, and hashed with MessageDigest.getInstance("SHA-256") before being persisted to email_verifications or password_resets.
  • Concurrency-Safe Reservation Locking: When a student clicks Reserve for Pickup or a seller clicks Accept, ReservationService acquires a database-level PESSIMISTIC_WRITE lock (`SELECT ... FOR UPDATE`) on the target Listing row, ensuring two simultaneous requests can never result in dual accepted reservations.

3.5 Exception Handling

All business rule violations throw checked/unchecked domain exceptions inheriting from SwapEdException:

  • ResourceNotFoundException (HTTP 404): Thrown when a requested listing, student, or reservation ID does not exist.
  • UnauthorizedActionException (HTTP 403): Thrown when a student attempts to edit/delete another student's listing or accept/complete another seller's reservation.
  • InvalidReservationException (HTTP 400): Thrown when a buyer attempts to reserve their own item, reserve an unavailable item, or complete a trade without an accepted reservation.
  • DuplicateResourceException (HTTP 400): Thrown when registering with an already-existing @thapar.edu email or Roll Number.
  • GlobalExceptionHandler (@ControllerAdvice): Intercepts domain exceptions and MaxUploadSizeExceededException, routing user-friendly flash messages or rendering templates/error/custom-error.html.

3.6 Collection Framework Usage

The Java Collections Framework is used extensively across the application:

  • List<Listing>, List<Reservation>, and List<Trade> for ordered query results and dashboard tables.
  • Set<Long> returned by WishlistRepository.findListingIdsByStudentId(...) to provide O(1) constant-time lookup when rendering heart icons across marketplace product cards.
  • Set<String> ALLOWED_CONTENT_TYPES = Set.of(...) in ListingService for immutable O(1) MIME-type whitelist validation during multipart image uploads.
  • Java Stream pipelines (myListings.stream().limit(4).toList()) in DashboardController for slicing recent activity collections cleanly.

3.7 Database Connectivity

Database connectivity is managed via HikariDataSource in DataSourceConfig.java and Spring Data JPA repositories. Schema creation is defined in src/main/resources/schema.sql and seeded via DataInitializerConfig.java using Spring's TransactionTemplate. All multi-table write operations (such as reservation acceptance and trade completion) execute inside @Transactional boundaries backed by MySQL InnoDB row-level locks.

3.8 Important Code Snippets

A. Custom @ThaparEmail Domain Validator (ThaparEmailValidator.java)

@Component
public class ThaparEmailValidator implements ConstraintValidator<ThaparEmail, String> {
    private static final Pattern EMAIL_STRUCTURE =
            Pattern.compile("^[A-Za-z0-9._%+-]+@[A-Za-z0-9.-]+\\.[A-Za-z]{2,}$");

    @Value("${swaped.auth.allowed-domain:thapar.edu}")
    private String allowedDomain;

    @Override
    public boolean isValid(String value, ConstraintValidatorContext context) {
        if (value == null || value.isBlank()) return false;
        String normalized = value.trim().toLowerCase();
        if (!EMAIL_STRUCTURE.matcher(normalized).matches()) return false;
        String domain = allowedDomain.trim().toLowerCase().replaceFirst("^@", "");
        return normalized.endsWith("@" + domain);
    }
}

B. Dynamic Marketplace Search & Pessimistic Locking Query (ListingRepository.java)

@Repository
public interface ListingRepository extends JpaRepository<Listing, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT l FROM Listing l WHERE l.listingId = :listingId")
    Optional<Listing> findByIdForUpdate(@Param("listingId") Long listingId);

    @Query("""
        SELECT l FROM Listing l JOIN FETCH l.seller s JOIN FETCH l.category c
        WHERE (:keyword IS NULL OR :keyword = '' OR
               LOWER(l.title) LIKE LOWER(CONCAT('%', :keyword, '%')) OR
               LOWER(l.description) LIKE LOWER(CONCAT('%', :keyword, '%')) OR
               LOWER(l.courseName) LIKE LOWER(CONCAT('%', :keyword, '%')) OR
               LOWER(l.courseCode) LIKE LOWER(CONCAT('%', :keyword, '%')) OR
               LOWER(c.categoryName) LIKE LOWER(CONCAT('%', :keyword, '%')))
          AND (:categoryId IS NULL OR c.categoryId = :categoryId)
          AND (:condition IS NULL OR l.itemCondition = :condition)
          AND (:availableOnly = FALSE OR l.listingStatus = com.swaped.entity.ListingStatus.AVAILABLE)
          AND (l.listingStatus <> com.swaped.entity.ListingStatus.INACTIVE)
        """)
    List<Listing> searchMarketplaceListings(
            @Param("keyword") String keyword,
            @Param("categoryId") Long categoryId,
            @Param("condition") ItemCondition condition,
            @Param("availableOnly") boolean availableOnly,
            Sort sort);
}

C. Pessimistic Locking & Atomic Reservation Acceptance (ReservationService.java)

@Transactional
public Reservation acceptReservation(Long reservationId, Long sellerId) {
    Reservation reservation = reservationRepository.findByIdForUpdate(reservationId)
            .orElseThrow(() -> new ResourceNotFoundException("Reservation not found."));
    Listing listing = listingRepository.findByIdForUpdate(reservation.getListing().getListingId())
            .orElseThrow(() -> new ResourceNotFoundException("Associated listing not found."));

    if (!listing.getSeller().getStudentId().equals(sellerId)) {
        throw new UnauthorizedActionException("Only the seller can accept reservation requests.");
    }
    if (reservation.getReservationStatus() != ReservationStatus.PENDING || !listing.isAvailable()) {
        throw new InvalidReservationException("Reservation or listing is no longer eligible.");
    }

    reservation.setReservationStatus(ReservationStatus.ACCEPTED);
    reservationRepository.save(reservation);

    listing.setListingStatus(ListingStatus.RESERVED);
    listingRepository.save(listing);

    // Automatically reject competing PENDING requests for the same listing
    List<Reservation> otherPending = reservationRepository.findByListingListingIdAndReservationStatus(
            listing.getListingId(), ReservationStatus.PENDING);
    for (Reservation other : otherPending) {
        if (!other.getReservationId().equals(reservationId)) {
            other.setReservationStatus(ReservationStatus.REJECTED);
            reservationRepository.save(other);
        }
    }
    return reservation;
}

C. Handover Confirmation & Trade Recording (TradeService.java)

@Transactional
public Trade confirmHandoverAndCompleteTrade(Long reservationId, Long sellerId) {
    Reservation reservation = reservationRepository.findByIdForUpdate(reservationId)
            .orElseThrow(() -> new ResourceNotFoundException("Reservation not found."));
    Listing listing = listingRepository.findByIdForUpdate(reservation.getListing().getListingId())
            .orElseThrow(() -> new ResourceNotFoundException("Listing not found."));

    if (!listing.getSeller().getStudentId().equals(sellerId)) {
        throw new UnauthorizedActionException("Only the seller can confirm handover.");
    }
    if (reservation.getReservationStatus() != ReservationStatus.ACCEPTED) {
        throw new InvalidReservationException("Reservation must be ACCEPTED before completing trade.");
    }

    reservation.setReservationStatus(ReservationStatus.COMPLETED);
    reservationRepository.save(reservation);
    listing.setListingStatus(ListingStatus.SOLD);
    listingRepository.save(listing);

    Trade completedTrade = new Trade(
            listing, reservation.getBuyer(), listing.getSeller(),
            listing.getSellingPrice(), TradeStatus.COMPLETED);
    return tradeRepository.save(completedTrade);
}
